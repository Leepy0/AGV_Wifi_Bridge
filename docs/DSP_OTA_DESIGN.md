# 메인보드(TMS320F2808) OTA 설계 — B안: 상주 부트로더

> 상태: 구현됨 (부트로더 `dsp/boot`, 앱 지원 `dsp/app`, 브리지 `main/dsp_ota.c`, 패커 `tools/dsp_pack.py`, PC 프로그래머 `tools/dsp_flash.py`). 실기 검증 전.
> 기준: 브리지 **v0.5.2** · 게이트웨이 **v0.3.0**. 시간·코드 값은 `main/dsp_ota.c`, `dsp/boot/boot_cfg.h` 기준.
> 범위: DSP 부트로더 · 메인보드 앱 수정 · 브리지(ESP32) · 패커 · 펌웨어 관리 서버(게이트웨이, 구현됨).

## 1. 전체 구조

```
┌──────────────────┐  HTTP(이미지)      ┌──────────┐  UART 115200   ┌─────────────────┐
│ 펌웨어 관리 서버  │ ───────────────▶ │ 브리지    │ ─────────────▶ │ 메인보드 F2808   │
│ (Gateway 와 통합) │  UDP(명령/결과)   │ ESP32-S3 │  J4 (SCI-A)    │ 부트로더 + 앱     │
│ 이미지·대상·이력  │ ◀─────────────── │ 이미지 보관│ ◀───────────── │                 │
└──────────────────┘  heartbeat(버전)   └──────────┘                └─────────────────┘
```

- 서버는 **이미지 저장·대상 선정·실행 명령·진행 기록·버전 이력**을 맡는다. 장치는 상태를 보고만 한다 (서버가 기록의 원본).
- 브리지는 이미지를 미리 받아 자기 플래시에 보관(**스테이징**)하고, 서버의 적용 명령을 받으면 메인보드를 부트로더로 보내 로컬 UART 로 프로그래밍한다. Wi-Fi 상태는 프로그래밍 시간에 영향을 주지 않는다.
- 부트로더는 플래시 섹터 A 에 상주하며 절대 지우지 않는다. 앱 영역(섹터 B~D)만 교체한다.

### 업데이트 흐름

```
① 서버: 이미지 업로드 → 작업 생성(대상 호기 선택)
② 서버 → 브리지: DSP_OTA_START {url, ver, crc32, size, job, apply}
③ 브리지: URL 호스트 확인 → HTTP 수신(머리 160 B 먼저 검사) → dspfw 파티션에 저장
          → 파일 CRC·버전·블록 구조 확인 → "staged" 보고                       (주행 중에도 가능)
   게이트웨이 기본: 전 호기 ③ 을 끝내고 '적용 대기' → 운용자가 AGV 정지를 확인하고 '적용 시작'
④ 서버 → 브리지: DSP_OTA_APPLY {job[, recover]}  (같은 job 번호. apply=1 이면 ③ 직후 자동.
                                                   recover 는 게이트웨이에서 운용자가 '복구 적용' 을 고른 작업만)
⑤ 브리지: 지우기 전 스테이징 이미지 재검사 → 앱에 `F…U000` → 앱이 정지 상태 확인 후 `R…UOK`,
          부트플래그 기록, 워치독 리셋
          (U 2초 무응답: 최근 3초 안에 앱 프레임이 있으면 app_no_fwup. 앱이 조용하면 복구 적용·버전 '?' 일 때만 ⑥ 으로 직행,
           아니면 app_no_reply 로 끝내고 버전을 '?' 로 — 6절 '앱 무응답과 복구 적용')
⑥ 브리지: J4 를 115200 으로 전환 → 부트로더: 플래그 확인 → 업데이트 모드 → HELLO (1.5초 × 3번)
          (복구 적용에서 HELLO 무응답이면 wait_power: 60초 동안 HELLO 50ms 간격, 전원 재투입 대기.
           복구 적용이 아니면 바로 no_bootloader)
⑦ 브리지: ERASE(B~D) → WRITE(블록) → 헤더 마지막 → VERIFY → RESET   (지운 뒤 실패하면 HELLO 부터 최대 2회 재시도)
⑧ 브리지: main_baud 로 복귀 → 앱 기동 → `F…V000` 으로 버전 확인(정확히 일치) → "done {ver}" 보고 → 서버가 이력 기록
실패: 어느 단계든 "fail {err}" 보고. 적용 단계 실패면 이미지는 스테이징된 채 남는다. 같은 job 의 재명령은 10분 동안 결과만 다시 보고하므로
      다시 하려면 새 작업(새 job 번호로 다시 스테이징)을 만든다
```

## 2. 메인보드 메모리 배치

### 플래시 (64K 워드, 섹터 4개)

| 영역 | 주소 (워드) | 용도 |
|---|---|---|
| 섹터 D | 0x3E8000 – 0x3EBFFF | 앱 (앱 헤더 + 코드) |
| 섹터 C | 0x3EC000 – 0x3EFFFF | 앱 |
| 섹터 B | 0x3F0000 – 0x3F3FFF | 앱 |
| 섹터 A | 0x3F4000 – 0x3F7F7F | **부트로더** (OTA 로 교체 불가) |
| 예약 | 0x3F7F80 – 0x3F7FF5 | CSM 미사용 → 0xFFFF 유지 |
| BEGIN | 0x3F7FF6 – 0x3F7FF7 | `LB _c_int00` (부트로더 진입) |
| CSM 비밀번호 | 0x3F7FF8 – 0x3F7FFF | **0xFFFF 유지. 0x0000 쓰면 영구 잠김.** 부트로더 READ 로도 읽히지 않음 |

앱 영역 = 0x3E8000 – 0x3F3FFF, **48K 워드(96KB)**. 현재 앱이 이 안에 들어가야 한다 (.map 의 FLASH 사용량 확인).

| 앱 영역 내부 | 주소 | 내용 |
|---|---|---|
| 앱 헤더 | 0x3E8000 – 0x3E803F (64 워드) | 아래 3절. **프로그래밍 때 맨 마지막에 씀** |
| 앱 codestart | 0x3E8040 | `LB _c_int00` — 부트로더가 여기로 점프 |
| 앱 코드·상수 | 0x3E8042 – 0x3F3FFF | 링커 cmd 로 배치 |

부트로더 정보 블록 (앱이 읽어 보고용): 0x3F7F00 – 0x3F7F3F (64 워드) — magic, 부트로더 버전 문자열, 프로토콜 버전.

### RAM (18K 워드)

| RAM | 주소 | 부트로더 | 앱 |
|---|---|---|---|
| M0 | 0x000000 – 0x0003FF | 스택 | 앱 자유 |
| M1 | 0x000400 – 0x0007F9 | `.bss` (대형 메모리 모델이라 거의 비어 있음) | 앱 자유 |
| **부트 카운터** | **0x0007FA – 0x0007FB (2 워드)** | magic + 연속 기동 실패 수. 점프 전 +1 | `fwup_boot_ok()` 로 0. **양쪽 링커 cmd 에서 제외** |
| **부트플래그** | **0x0007FC – 0x0007FF (4 워드)** | 읽고 지움 | 쓰기만. **양쪽 링커 cmd 에서 제외** |
| L0 | 0x008000 – 0x008FFF | 플래시 API + 쓰기 루틴 (ramfuncs) | 앱 자유 |
| L1 | 0x009000 – 0x009FFF | `.ebss` — 전역 변수 (프로토콜 수신·송신 버퍼 포함) | 앱 자유 |
| H0 | 0x3F8000 – 0x3F9FFF | 미사용 | 앱 자유 |

부트로더와 앱은 동시에 돌지 않으므로 RAM 을 겹쳐 써도 된다. 부트 카운터·부트플래그 6 워드만 둘 다 건드리지 않는다. SARAM 은 워치독 리셋을 거쳐도 내용이 남는다(전원 차단 시에만 소실 — 부트 카운터는 magic 이 깨지므로 0 으로 취급).

## 3. 앱 이미지 형식

패커(`tools/dsp_pack.py`)가 CCS 빌드 결과에서 만든다. 서버에 올리는 파일이자 브리지가 보관하는 파일.

### 앱 헤더 (플래시 0x3E8000, 64 워드)

| 워드 | 내용 |
|---|---|
| 0 | magic0 = 0xA55A |
| 1 | magic1 = 0x4650 ('FP') |
| 2 | 헤더 형식 버전 = 1 |
| 3 | flags (예약, 0) |
| 4–5 | app_len: 코드 길이(워드), 0x3E8040 부터. 리틀 엔디언(하위 워드 먼저) |
| 6–7 | app_crc32: [0x3E8040, 0x3E8040 + app_len) 의 CRC32 |
| 8–9 | build_time: UTC unix 초 |
| 10–41 | version: 32 워드 칸 (C28x 는 char 가 16비트 → 워드당 1문자), NUL 종료. **실제 규칙은 1~8자** (아래) |
| 42–61 | 예약 (0xFFFF) |
| 62 | hdr_crc16: 워드 0–61 의 CRC16 |
| 63 | ~hdr_crc16 |

CRC32: 표준(poly 0xEDB88320, init 0xFFFFFFFF, 최종 XOR). 워드마다 **하위 바이트, 상위 바이트 순**으로 넣는다. CRC16: CRC-16/CCITT-FALSE(poly 0x1021, init 0xFFFF), 같은 바이트 순서. 패커·부트로더·브리지가 모두 같은 구현을 쓴다(테스트 벡터를 문서에 고정).

**유효 조건**: magic 일치 ∧ hdr_crc 일치 ∧ app_crc32 일치. 쓰다가 끊기면 셋 중 하나가 반드시 깨진다.

**버전 규칙 (필수)**: 영문·숫자·`.` `_` `-` 로 1~8자 (예: `1.2.3`). 앱의 `R` 응답 버전 칸이 8자 고정이라서다. 패커는 어기면 거부하고, 브리지는 앱 헤더 버전이 이 규칙을 지키고 파일 헤더 버전과 같아야 받는다(`ver_invalid`). 게이트웨이도 업로드 때 같은 규칙으로 거부한다.

### 이미지 파일 (`*.dspfw`)

```
[파일 헤더 32 B] magic "AGVDSP1\0", total_len, image_crc32, ver(16 B ASCII)
[앱 헤더 64 워드 = 128 B]
[블록 N개] 각 블록: addr(u32, 워드 주소) len(u16, 워드 수) data[len 워드, 리틀 엔디언 바이트쌍]
```
- 0xFFFF 로만 채워진 구간은 블록에서 뺀다 (전송량 절감).
- 블록마다 len 1~128, 주소는 0x3E8040 – 0x3F3FFF 안, **주소 오름차순·겹침 없음**, 마지막 블록이 파일 끝과 정확히 맞아야 한다. 패커 출력은 늘 이 순서다. 패커가 파일을 읽을 때(`dsp_pack.py info`, `dsp_flash.py`)도 같은 규칙으로 검사해, 다른 도구로 만들었거나 블록 순서를 바꾼 파일은 거부한다.
- 브리지는 빈 구간을 0xFFFF 로 채워 복원한 CRC32 가 app_crc32 와 같은지까지 본다. 스테이징할 때와 메인보드를 지우기 전에 검사하고, 어기면 `image_bad`.
- 범위 밖 주소는 패커가 거부하고, 부트로더도 거부한다.
- 서버는 파일 헤더의 ver·crc 를 그대로 DB 에 올린다.

### 패커 입력

`hex2000 -i -o app.hex app.out --memwidth=16 --romwidth=16` 의 Intel HEX. 이 옵션에서 주소는 **워드 단위**, 각 워드는 **상위 바이트 → 하위 바이트** 순으로 기록된다(컴파일러 18.12.8 로 실측). 바이트 주소(0x7D0000 대, `--romwidth=8` 등)로 나오면 패커가 **거부**한다 — 워드 재조립과 바이트 순서를 추측하면 CRC 는 맞지만 내용이 틀린 이미지가 만들어질 수 있기 때문. 버전은 `--ver 1.2.3` 인자로 준다.

## 4. 부트로더 (섹터 A)

### 리셋 후 동작

```
1. 워치독 정지, PLL·클럭 설정 (앱과 동일 값 — 크리스탈·PLLCR·DIVSEL 확인 필요)
   플래시 대기 상태 RANDWAIT 3 · PAGEWAIT 3 · OTPWAIT 5 (100MHz 데이터시트 최소값)
2. ramfuncs(플래시 API + 쓰기 루틴) 를 L0 로 복사
3. 부트플래그(0x0007FC) 가 0xB007/0x1DEA/0x5AFE/0xC0DE 이면 → 지우고 업데이트 모드 (첫 패킷 시한 60초)
4. 앱 헤더 검사 (magic, hdr_crc, app_crc32 — 48K 워드 CRC 는 수 ms)
   유효 → 부트 카운터(0x0007FA) +1. 3 을 넘으면(앱이 `fwup_boot_ok()` 없이 연속 리셋 = CRC 는 맞지만 기동 불능)
          카운터를 지우고 업데이트 모드.
        → 아니면 HELLO 수신 창: 200ms 동안 SCI-A 115200 에서 CRC 가 맞는 HELLO 만 받는다.
          HELLO 를 받으면 응답하고 카운터를 지우고 업데이트 모드.
          없으면 SCI-A·CPU 타이머0 을 리셋 기본값으로(GPIO 는 원래 값으로) 되돌리고 0x3E8040 으로 점프
   무효 → 업데이트 모드
5. 업데이트 모드: SCI-A 115200 8N1, 프로토콜 대기. LED 표시는 없다(9절 7번).
```

| 진입 사유 | 첫 유효 패킷 전 | 첫 패킷 뒤 | 시한이 지나면 |
|---|---|---|---|
| 부트플래그 (앱이 `U000` 승인) | 60초 | 600초 유휴 | 앱이 유효하면 앱으로 리셋 |
| 부트 카운터 초과 | 600초 | 600초 유휴 | 앱이 유효하면 앱으로 리셋 |
| HELLO 창 | 600초 | 600초 유휴 | 앱이 유효하면 앱으로 리셋 |
| 앱 무효 | — | — | 리셋하지 않고 계속 대기 |

- 유효한 프로토콜 패킷만 유휴 시계를 되돌린다. 앱용 ASCII 프레임(V 조회·ACS·RFID)이나 노이즈는 아니다.
- 패킷 수신 도중 100ms 넘게 바이트가 끊기면 파서를 처음부터 (잘린 패킷이 다음 HELLO 를 삼키지 않도록). HELLO 창 안에서는 10ms.
- SCI 수신 오류(SCIRXST.RXERROR: 브레이크·프레이밍·오버런·패리티)가 나면 보내던 응답을 끝낸 뒤 SCI 를 HOLD→RUN 으로 리셋하고 RX FIFO 를 비운 다음 파서를 재동기한다. 쓰는 도중 브리지가 재부팅해도 전원 재투입 없이 HELLO 부터 이어 간다.
- **부팅 지연: 약 0.2초** (HELLO 창 200ms + 플래그 검사·CRC 수 ms). 창 길이는 고정이라 노이즈가 와도 늘어나지 않는다.
- HELLO 창의 목적: 리셋 없이 멈추거나 J4 통신이 안 되는 앱도 OTA 로 살리는 구조 경로. 브리지가 HELLO 를 50ms 간격으로 계속 보내는 동안 메인보드 전원을 다시 넣으면 이 창에서 잡힌다(6절 복구 적용). 이번 부팅은 앱을 실행하지 않으므로 기동 실패로 세지 않는다.
- 업데이트 모드에서 GPIO 는 SCI-A 핀(GPIO28/29) 말고는 리셋 기본값(입력) 그대로 둔다. 현재 전원 ON 직후와 같은 상태.
- 플래시 API: TI SPRC193 `Flash2808_API_V302.lib` (`F2808_boot.cmd` 가 이 이름으로 링크). RAM 실행, 지우기·쓰기 중 인터럽트 금지, `Flash_CPUScaleFactor` 를 SYSCLK 에 맞춤, 워치독 콜백.
- **섹터 A 지우기 명령은 없다.** 주소 검사로 0x3F4000 이상 쓰기를 거부한다.
- 부트로더 버전 문자열은 0.5.2 소스부터 `1.1.0` 이다(0.5.1 이전 소스는 `1.0.0`). 위 동작(HELLO 창, 60초 시한, 수신 오류 복구, OTPWAIT 5, READ 범위)이 바뀐 것을 게이트웨이 화면의 `dspb`(부트로더) 로 구분할 수 있다. 프로토콜 버전(1)은 그대로라 옛 부트로더도 0.5.2 브리지와 통신된다.

### 브리지 ↔ 부트로더 프로토콜 (SCI-A, 115200, 바이너리)

```
[0xC5][0x3A][len u16 LE][cmd u8][seq u8][payload len B][crc16 u16 LE]   crc16: cmd..payload
응답: cmd | 0x80, payload 첫 바이트 = status (0 OK, 그 외 오류코드)
```

| cmd | 이름 | payload | 응답 payload | 시간 |
|---|---|---|---|---|
| 0x01 | HELLO | — | status, proto_ver, max_block(u16, 워드), app_valid, boot_ver(16 B), app_ver(32 B), app_crc32(u32), app_len(u32, 워드) — 61 B | 즉시 |
| 0x02 | ERASE | 섹터 마스크 (bit0=B, bit1=C, bit2=D) | status — 1 B | 섹터당 1~2초 |
| 0x03 | WRITE | addr u32, nwords u16, data | status, addr u32 — 5 B | 128 워드 ≈ 30ms |
| 0x04 | VERIFY | — | status, app_valid(헤더·CRC 모두 맞으면 1), crc32 계산값(u32), app_len(u32), 검사 코드(`DSPIMG_*`) — 11 B | ~수 ms |
| 0x05 | RESET | 0 = 앱으로 | status 후 워치독 리셋 | — |
| 0x06 | READ | addr u32, nwords u16 | status, data | 진단용. 플래시 0x3E8000–0x3F7FF7 · OTP 0x3D7800–0x3D7BFF 만, 그 밖은 `BAD_ADDR` |

- 응답 순서·길이는 `dsp/common/bootproto.c` `handle()` 기준, 다중 바이트는 리틀 엔디언. HELLO 의 app_crc32·app_len 은 앱이 유효할 때만 값(아니면 0). 브리지는 HELLO·ERASE·WRITE·VERIFY 응답 길이가 다르면 실패로 본다.
- HELLO 창에서는 HELLO 만 처리하고 다른 명령은 응답 없이 버린다.
- 재전송 판정: seq·cmd·요청 길이·요청 CRC16 이 모두 직전과 같으면 다시 처리하지 않고 이전 응답을 반복한다. `tools/dsp_flash.py` 는 실행마다 seq 를 무작위 값에서 시작한다.
- WRITE 는 쓴 뒤 읽어 비교(Flash_Verify)까지 하고 응답한다.
- 쓰기 순서: 블록들 → **앱 헤더(0x3E8000) 마지막**.

### 브리지 ↔ 앱 프레임 (J4, 기존 AGV-ACS 프로토콜 형식)

기존 프레임 규격을 그대로 따른다: `STX` + 종류(1) + PAN ID(1) + MSG ID(1) + AGV ID(2) + 본문 + 공백 + BCC(1) + `ETX`. BCC 는 STX·ETX 를 뺀 바이트 합의 하위 니블을 ASCII-HEX 대문자로.

**새 종류 문자 `F`(브리지 → AGV) 와 `R`(AGV → 브리지) 는 현재 프로토콜 문서에 없는 값이다. 아래는 제안이며, 확정 후 프로토콜 문서에 등록한다.**

| 프레임 | 방향 | 본문 (헤더 뒤) | 예 (PAN 3, MSG 1, 07호기) |
|---|---|---|---|
| 버전 조회 | 브리지 → AGV | `V000` | `F3107V000 ` + BCC |
| 버전 응답 | AGV → 브리지 | `V` + 앱 버전 8자 + 부트로더 버전 8자 + 빌드일 8자(YYYYMMDD). 짧으면 공백 → **버전 문자열은 1~8자 필수** (예: `1.2.3`, `2.0.15`) | `R3107V1.2.3   1.1.0   20261008 ` + BCC |
| 업데이트 진입 | 브리지 → AGV | `U000` | `F3107U000 ` + BCC |
| 진입 응답 | AGV → 브리지 | `U` + `OK` 또는 `NG` + 사유 2자리 | `R3107UOK00 ` + BCC / `R3107UNG01 ` + BCC |

사유 코드(제안): `01` 주행 중, `02` 충전 중, `03` 전압 부족, `04` 에러 상태, `09` 기타(안전 콜백 없음 포함). 브리지는 `app_ng_01` 처럼 보고한다.

- `F` 프레임은 브리지가 만든다. PAN ID 는 그 호기의 `E` 이벤트에서 학습한 값(모르면 `1`), MSG ID 는 브리지 자체 카운터 `1`~`F`.
- 앱(`fwup_handle`)은 요청이 정확히 11자(`F` PAN MSG AGV2 `V`/`U` `000` 공백 BCC, PAN·MSG 는 `1`~`9`·`A`~`F`, 호기는 숫자 2자리)일 때만 처리한다. 하나라도 어긋나면 `FWUP_NONE` 이고 안전 콜백도 부르지 않는다.
- AGV 앱은 `F` 프레임을 ACS 의 ack·중복 판정 로직과 **분리**해서 처리한다 (MSG ID 가 ACS 패킷과 겹칠 수 있음). `F` 에 대한 `A` ack 는 보내지 않고 `R` 로 답한다.
- `R` 프레임은 브리지가 소비하고 서버로 올리지 않는다. `F`/`R` 외 프레임은 지금처럼 그대로 중계한다.
- 진입 응답 `UOK` 의 송신이 끝나면(`SCICTL2.TXEMPTY`) 앱은 `fwup_reset()` 으로 부트플래그를 기록하고 바로 워치독 리셋한다. 브리지는 `UOK` 를 받고 400ms(`BOOT_START_MS`) 뒤 HELLO 를 보낸다. 안전 조건(정지, 충전 아님, 전압 정상, 에러 없음)은 메인보드 기준으로 정의한다.
- 브리지 쪽 프레임 생성·해석은 `main/dsp_app_proto.h/.c` 한 곳에 두고 BCC 는 레퍼런스의 테스트 벡터(`H`→`8`, `12345678`→`4`)로 검증한다. 호스트 시험(`tests/host/test_fwup.c`)이 브리지가 만든 F 프레임을 앱 코드가 처리하고, 앱의 R 응답을 브리지가 해석하는 계약을 함께 본다.
- 체크섬이 4비트라 수신 측은 길이·종류·자리별 문자 범위도 같이 검사한다.

### UDP 패킷 추가

| type | 방향 | payload |
|---|---|---|
| `0x11` INFO_REQ | 서버 → ESP | 없음 |
| `0x12` INFO | ESP → 서버 | JSON: agv, mac, ip, fw(ESP), part, ota, cfg, setup, up, dsp(앱 버전), dspb(부트로더 버전), dsp_build, dsp_st, staged{job, ver} |
| `0x32` DSP_OTA_START | 서버 → ESP | JSON: url(199자 이하), ver, crc32, size, job, apply(0/1), recover(선택, 1) |
| `0x33` DSP_OTA_RESULT | ESP → 서버 | JSON: job, stage, pct, ver, err (아래 표) |
| `0x34` DSP_OTA_APPLY | 서버 → ESP | JSON: job, recover(선택, 1 = 복구 적용) |

- heartbeat(STATUS) 에 `mac`, `dsp`, `dspb`, `dsp_build`, `dsp_st`, `staged` 필드가 있다. 서버는 이것으로 전 호기 버전 현황을 갱신하고, 최종 보고가 유실돼도 `staged.job`·`dsp`·`dsp_st` 로 판정한다.
- 브리지는 부팅 3초 뒤, 그리고 DSP 업데이트 후에 버전 조회(`F…V000`)를 보내 `dsp`/`dspb` 를 갱신한다. 응답이 없으면 `dsp`·`dsp_build` 를 `"?"` 로 바꾼다(미지원 구 펌웨어, 앱 없음, 멈춘 앱. `dspb` 는 마지막으로 안 값을 유지). `"?"` 인 동안 60초마다 다시 묻는다. 콘솔 `dsp ver` 도 같은 규칙이다. 송신 실패(대기열 가득)는 버전을 그대로 둔다.
- 지우기를 시작할 때와, 적용에서 앱이 조용해 `app_no_reply` 로 끝날 때도 `"?"` 로 바꾼다. 버전을 아는 동안에는 주기 조회를 하지 않으므로, 앱이 나중에 멈추면 다음 적용 시도나 `dsp ver` 때 `"?"` 가 된다.

#### DSP_OTA_RESULT stage

| stage | pct | 뜻 |
|---|---|---|
| `download` | 0~100 (20% 단위) | 스테이징 받는 중 |
| `staged` | 100 | 스테이징 끝 (`ver` 포함) — 최종 보고 |
| `start` | 0 | 적용 시작 (`ver` = 스테이징 버전) |
| `enter` | — | 앱에 `U` 요청 |
| `wait_power` | — | 복구 적용: 부트로더 무응답, 전원 재투입 대기 (10초마다 반복, 최대 60초) |
| `erase` | — | 메인보드 앱 영역 지우기 |
| `retry` | n (1~2) | 지운 뒤 실패해 HELLO 부터 n 번째 재시도 |
| `progress` | 0~100 (10% 단위) | 블록 쓰기 |
| `verify` | — | 검증 |
| `done` | 100 | 완료 (`ver` = 앱이 보고한 버전) — 최종 보고 |
| `fail` | — | 실패 (`err`) — 최종 보고 |

최종 보고(`staged`·`done`·`fail`)는 같은 내용을 약 300ms 간격으로 3번 보낸다. 서버 수신 단계에서 바로 거부하는 것(`bad_request`·`url_too_long`·`url_host`·`busy`·`not_ready`)은 간격 없이 3번 보낸다.

| 확인 | `ver_mismatch` | 앱이 보고한 버전 ≠ 이미지 버전 (정확히 비교) | 유지 |

- '유지' 는 이미지가 스테이징된 채 남는다는 뜻이다. 다만 같은 job 의 APPLY 는 10분 동안 마지막 결과만 다시 보고하므로, 다시 하려면 새 job 으로 스테이징부터 한다(게이트웨이는 작업마다 새 job 번호를 쓴다). job 0(콘솔 `dsp apply`)은 중복 판정을 하지 않는다.
- 게이트웨이는 안내 표(`Gateway.Core/Fota/DspOtaClient.cs` 의 `BridgeErrors`)에 있는 코드에 한국어 안내를 붙여 작업 로그에 보인다. 표에 없는 코드는 코드만 보인다.

### 프로그래밍 중 UART 독점

- `uart_bridge` 원시 모드: ETX 프레이밍 해제, RFID→메인보드 바이패스 정지, 서버 MAIN_DOWN 폐기(카운트), 프로그래밍 태스크가 바이트 단위로 읽고 씀. 끝나면 복귀.
- 원시 모드에 들어갈 때 송신이 끝나기를 기다린 뒤 J4 를 **115200**(부트로더 고정 속도)으로 바꾸고, 나올 때 마지막 패킷(RESET 등)이 다 나간 뒤 `main_baud` 로 되돌린다. `U`/`UOK` 는 `main_baud` 로, HELLO 부터 RESET 까지는 115200 으로 오간다.
- 조건: 브리지 자체 OTA 가 진행 중이면 거부(`esp_ota_busy`). 상태를 먼저 세운 뒤 상대 플래그를 보므로(양쪽 모두) 메인보드 적용과 브리지 OTA 가 동시에 시작해도 한쪽은 반드시 물러난다. 스테이징 이미지는 지우기 전에 파일 CRC·버전·블록 구조·복원 CRC 를 다시 검사한다.
- 굽는 중에는 브리지 `reboot`(서버·BLE·콘솔)과 브리지 OTA(`mainboard_programming`)를 거부한다. 받는 중(스테이징)에도 브리지 OTA 는 거부한다(`mainboard_staging`).

### 앱 무응답과 복구 적용

앱이 `U` 에 2초 안에 응답하지 않을 때, 브리지는 먼저 앱이 살아 있는지 본다. 기준은 최근 3초(`APP_ALIVE_MS`) 안에 J4 에서 받은 앱 프레임이다. 앱 프레임은 STX 로 시작하는 8바이트 이상 프레임이고, 원시 모드 중에 받은 것(부트로더 응답·노이즈)은 세지 않는다.

| 앱 상태 | `recover` | 브리지 동작 |
|---|---|---|
| 최근 3초 안에 앱 프레임이 옴 (살아 있으나 `U` 미지원) | 상관없음 | `app_no_fwup`. 원시 모드로 가지 않음 |
| 조용함 | 1 | 원시 모드 → HELLO 3번 → 안 되면 `wait_power` (최대 60초) |
| 조용함, 앱 버전 `?` | 없음 | 원시 모드 → HELLO 3번만 (약 4.5초), 안 되면 `no_bootloader` |
| 조용함, 앱 버전 앎 | 없음 | `app_no_reply`. 버전을 `?` 로 바꿈 (앱이 살아 있으면 60초 재조회로 돌아옴) |

원시 모드에 들어가면 RFID·ACS 중계가 멈추므로, 앱이 살아 있을 수 있는 경우에는 들어가지 않는다.

- `recover:1` 인데 HELLO 3번이 모두 무응답이면 `wait_power`: 60초 동안 HELLO 를 50ms 간격으로 보내고(10초 묶음마다 seq 하나), 10초마다 `wait_power` 를 보고한다(서버는 보고가 올 때마다 대기 시한을 늘린다). 그동안 메인보드 전원을 다시 넣으면 부트로더의 HELLO 창(4절)에서 잡혀 굽기를 이어 간다. 끝내 안 잡히면 `no_bootloader`.
- 게이트웨이 0.3.0 은 운용자가 새 작업에서 **복구 적용** 을 켠 메인보드 작업에만 `recover:1` 을 싣는다(재전송 포함). heartbeat `dsp` 가 `?` 라는 것만으로는 붙이지 않는다. 살아 있는 구 앱 호기가 원시 모드에 오래 묶이지 않게 하려는 것이다. `recover` 가 있어도 브리지는 먼저 `U` 를 보내므로, 앱이 살아 있으면 평소처럼 앱의 정지 확인을 거친다.
- 버전 `?` 인 호기에 일반 적용을 보내면, 앱이 조용할 때 HELLO 3번(약 4.5초)만 시도한다. 앱이 지워져 부트로더가 업데이트 모드에서 기다리는 호기(첫 설치, 지운 뒤 실패)는 이것으로 굽힌다. 앱이 멈춰 부트로더가 듣지 않으면 `no_bootloader` 로 끝나고, 게이트웨이는 '복구 적용으로 다시 배포(앱이 멈춘 경우)' 를 안내한다.
- 버전을 알던 앱이 멈춘 호기는 이렇게 진행된다: 일반 적용 → `app_no_reply`, 버전 `?` → (부트로더가 기다리면) 다음 일반 적용으로 굽힘, (아니면) '복구 적용' 작업 → `wait_power` 때 전원 재투입.
- 앱 생존 판단의 한계: 앱이 프레임을 3초보다 드물게 보내면(예: ACS 가 묻지 않으면 E/A 를 보내지 않는 앱) 살아 있어도 '조용함' 으로 본다. 그런 구 앱 호기에 '복구 적용' 을 보내면 원시 모드에서 약 65초(HELLO 3번 약 4.5초 + `wait_power` 60초) 중계가 끊긴 뒤 `no_bootloader` 로 끝난다. `U` 를 지원하는 앱은 `U` 응답이 먼저라 상관없다.
- 0.5.1 이전 소스의 부트로더에는 HELLO 창이 없어 전원 재투입 복구가 되지 않는다.

### 실패 시 재시도

- 패킷 단위: `bl_xfer` 가 같은 seq 로 3회(`RETRIES`). HELLO 는 1.5s × 3 = 4.5초.
- 절차 단위: **ERASE 를 보낸 뒤** 실패하면 `U` 없이 HELLO → ERASE → WRITE → 헤더 → VERIFY 를 최대 2번 더 하고, 시도마다 `retry` 를 보고한다. 부트로더는 앱이 무효한 동안 업데이트 모드에 머물러 있으므로 HELLO 가 바로 잡힌다.
- HELLO 이전 실패(`app_ng_NN`, `app_no_fwup`, `app_no_reply`, `uart_busy`, `no_bootloader`, `boot_proto`)는 메인보드를 건드리지 않았으므로 재시도하지 않는다.
- 끝내 실패하면 `fail` 보고로 끝내고 이미지는 남겨 둔다(`staged`). 메인보드에 앱이 없으면 부트로더가 업데이트 모드에서 기다리고 `dsp` 는 `?` 다. 앱 프레임도 없으므로 다음 작업은 일반 적용으로도 HELLO 로 바로 굽는다.

### 같은 job 의 중복 명령 (서버 재전송)

job ≠ 0 인 명령에만 적용한다. 판정은 상태를 쓰는 dsp 태스크 한 곳에서 한다.

| 상황 | 브리지 동작 |
|---|---|
| 그 job 의 START 를 처리하는 중(받기, `apply:1` 이면 이어지는 적용까지)에 같은 START, 그 job 을 굽는 중에 같은 APPLY | 무시 (보고 없음). 그 밖의 경우는 큐에서 기다렸다가 아래 규칙으로 처리 |
| 이미 스테이징된 job 의 START | 다시 받지 않고 `staged` 를 다시 보고 (`apply:1` 이면 적용 단계 판정으로) |
| 10분 안에 같은 job 의 결과가 있음 (받기 실패, 적용 `done`·`fail`) | 다시 받거나 굽지 않고 그 결과를 다시 보고 (3번) |
| 10분이 지났거나 브리지가 재부팅함 | 처음 명령처럼 처리 (예: 적용 뒤 스테이징이 지워졌으면 `not_staged`) |
| 다른 job | 지금까지와 같음 (`job_mismatch` 등) |

브리지는 가장 최근 결과 1건만 기억한다. 그래서 `done` 뒤에 재전송된 APPLY 가 `not_staged` 로 오판되지 않는다.

## 7. 펌웨어 관리 서버 (구현됨 — 게이트웨이)

게이트웨이 [AGV_FOTA_GATEWAY](https://github.com/Leepy0/AGV_FOTA_GATEWAY)(ASP.NET Core, Windows 서비스)로 구현되었다. 브리지와 UDP 50000 으로 같은 패킷을 주고받고, 펌웨어 파일은 HTTP 8080 으로 내준다. 흐름은 [SYSTEM_FLOW.md](https://github.com/Leepy0/AGV_FOTA_GATEWAY/blob/main/docs/SYSTEM_FLOW.md), 설치·운영은 [DEPLOY.md](https://github.com/Leepy0/AGV_FOTA_GATEWAY/blob/main/docs/DEPLOY.md). BridgeTest.cs 는 벤치용 참조 구현으로 남는다.

게이트웨이 0.3.0 의 메인보드 작업은 아래 3번 '실행' 을 이렇게 구현한다.

- 기본(스테이징 후 확인하고 적용): 전 호기 스테이징 → 작업이 '적용 대기' 에서 멈춤 → 운용자가 AGV 정지를 확인하고 '적용 시작' → 한 대씩 APPLY (스테이징 때와 같은 job 번호).
- 바로 적용(야간 예약용): 호기마다 스테이징 직후 바로 APPLY. 만들 때 확인창에서 정지 확인을 받는다.
- 메인보드 작업에는 '복구 적용' 선택이 있다. 켠 작업만 모든 APPLY(재전송 포함)에 `recover:1` 을 싣는다(6절 '앱 무응답과 복구 적용').
- 스테이징 URL 은 `PublicBaseUrl`(비우면 호기 쪽 NIC 의 IP)로 만든다. 호스트가 브리지의 `server` IP 와 같은 IPv4 여야 브리지가 받는다. 199자를 넘으면 START 전에 실패시킨다.
- 명령 뒤 5초 동안 수신 흔적이 없으면 같은 명령을 다시 보낸다(최대 3번). 적용 뒤 버전은 앞 8자로 비교하고 heartbeat 로 30초 동안 확인한다.

아래 데이터·기능은 처음 설계안이다. 실제 구현은 게이트웨이 문서를 본다.

### 데이터

| 테이블 | 필드 |
|---|---|
| devices | agv_id(PK), mac, last_ip, esp_fw, esp_part, esp_ota_state, dsp_ver, dsp_boot_ver, dsp_build, cfg_state, rssi, last_seen, staged_job |
| images | id, kind(esp/dsp), ver, file_path, size, crc32/sha256, uploaded_at, uploaded_by, note |
| jobs | id, image_id, kind, mode(stage/apply), created_at, created_by, state(open/done/cancelled), note |
| job_items | job_id, agv_id, state(queued/staged/programming/done/failed), pct, started_at, finished_at, before_ver, after_ver, error |
| events | ts, agv_id, job_id, stage, detail (DSP_OTA_RESULT·OTA_RESULT 원문) |

### 기능

1. **이미지 관리**: 업로드(.dspfw / ESP .bin) → 헤더에서 ver·crc 추출 → HTTP 로 서비스 (`/fw/<id>`).
2. **대상 선정**: 호기 목록(버전·접속·상태) 에서 선택, 필터(현재 버전 ≠ 대상 버전, 접속 중, 정지 중).
3. **실행**: 스테이징(즉시, 병렬 가능) → 적용(정지 확인 후. ACS 상태 연동 또는 수동 "지금 적용"). 동시 적용 수 제한 옵션.
4. **진행·기록**: 결과 패킷을 job_items/events 에 기록. 완료 시 before/after 버전과 시각. heartbeat 의 `dsp` 가 대상 버전과 일치해야 완료로 인정.
5. **이력 조회**: 호기별 업데이트 이력, 버전별 호기 수, 실패 목록과 사유.
6. **롤백**: 이전 이미지를 골라 같은 절차로 재설치 (슬롯 롤백은 없음).
7. **ESP OTA 도 같은 작업 모델**로 다룬다 (kind=esp, 기존 OTA_START/OTA_RESULT).

시각은 서버 기준으로 기록한다. 장치에는 RTC 가 없다.

## 8. 안전·운용 규칙

- 적용은 **정지 상태**에서만. 이중 확인: 게이트웨이가 '적용 시작'(또는 바로 적용 작업을 만들 때) 확인창에서 운용자의 정지 확인을 받고, 앱의 `U000` 진입 조건(safe 콜백)이 메인보드 기준으로 한 번 더 본다. safe 콜백은 필수다(NULL 이면 항상 거부).
- 적용 중 메인보드는 앱을 돌리지 않는다(약 20~30초). 이 동안 RFID 바이패스도 멈춘다.
- 전원이 끊기면 앱 헤더가 깨진 채 남고, 다음 부팅에 부트로더가 대기한다. 서버에서 새 작업으로 다시 적용한다(앱 버전 `?`·앱 침묵이라 일반 적용도 HELLO 로 바로 들어간다).
- 기동 직후 리셋되는 앱(링커 cmd·클럭 초기화 실수로 예외·워치독 리셋이 반복)이 올라가면 리셋 3회 뒤 부트로더가 업데이트 모드로 들어가므로 고친 이미지를 다시 적용하면 된다. 그래서 앱은 메인 루프 진입 시 `fwup_boot_ok()` 를 반드시 호출한다.
- **리셋 없이 멈추는 앱**(워치독을 끈 채 무한 대기 등)이나 메인 루프까지 가지만 J4 SCI 가 안 되는 앱은 부트 카운터로 못 잡는다. 앱 워치독을 필수로 하고, 그래도 멈추면 '복구 적용' 작업에서 `wait_power` 가 뜬 뒤 60초 안에 메인보드 전원을 다시 넣는다(HELLO 창).
- 버전을 보고하던 앱이 나중에 멈추면 첫 적용은 `app_no_reply` 로 끝나고 브리지가 `dsp` 를 `?` 로 바꾼다. 부트로더가 업데이트 모드에 있으면(워치독 리셋 반복 등) 다음 일반 적용으로 굽힌다. 부트로더도 응답하지 않으면 운용자가 '복구 적용' 을 켠 작업으로 다시 배포하고 전원을 재투입한다.
- OTA 지원 코드(`fwup_handle`)가 없는 구 앱은 프레임을 계속 보내므로 `app_no_fwup` 으로 거부된다('복구 적용' 이어도 같다). 원시 모드로 들어가지 않아 주행 중인 호기의 중계를 끊지 않는다. 지원 코드를 넣은 앱을 JTAG 으로 한 번 굽는다.
- 지우기 뒤 실패하면 브리지는 메인보드 버전을 `?` 로 보고한다(앱 없음). 서버 현황판에서 `?` 인 호기는 새 작업으로 다시 적용한다.
- 서버의 이미지 URL 은 리다이렉트 없이 200 으로 바로 주는 것이 좋다 (브리지는 3xx 를 3회까지만 따라가고, 리다이렉트 대상도 `server` IP 여야 한다).
- 브리지 OTA·스테이징 URL 은 출처(호스트 = `server` IP)만 제한하고 서명은 검사하지 않는다. 사내망 전제다.
- 부트로더는 OTA 로 못 고친다. 배포 전 벤치에서 충분히 검증(전원 차단·케이블 분리·잘못된 이미지·CRC 오류 주입). 현장 설치 전에 0.5.2 소스로 굽는다.
- 첫 설치(부트로더 + 재링크 앱)는 호기마다 유선(JTAG 또는 SDFlash) 1회.

| 3 | SCI-A GPIO28/29, 115200 | 적용 |
| 4 | 종류 문자 `F`/`R` | 적용 (프로토콜 문서 등록 필요) |
| 5 | CCS 9.1.0 (컴파일러 18.12.x), Flash API SPRC193 다운로드 | 부트로더는 18.12.8 로 컴파일·링크 확인 (Flash API 는 스텁으로 링크) |
| 6 | CSM 0xFFFF | 확인됨 |
| 7 | LED 없음 | 표시 없음 |
| 8 | 부팅 0.2초 지연 | HELLO 창 때문에 앱 시작이 약 0.2초 늦어짐 — 메인보드 기동 시간 조건과 충돌하지 않는지 실기 확인 |

## 10. 구현 순서

1. 패커 + 이미지 형식 + CRC 테스트 벡터 (호스트 테스트)
2. 부트로더 소스·링커 cmd·앱 수정 예시 → CCS 빌드 → JTAG 으로 벤치 검증 (PC 에서 `tools/dsp_flash.py` 로 직접 시리얼 프로그래밍)
3. 브리지: 파티션, 패킷, 스테이징, UART 원시 모드, 프로그래밍 클라이언트, INFO/heartbeat
4. BridgeTest: `dspota stage/apply/info` 명령 (서버 참조 구현). `apply` 는 그 호기에 마지막으로 stage 한 job 을 한 번만 쓰고(적용한 job 은 잊음 — 같은 job 재적용은 replay_recent 로 이전 결과만 옴), 도구를 다시 띄웠으면 `dspota 7 apply [recover] <job>` 으로 heartbeat `staged.job` 을 준다
5. 관리 서버 — 게이트웨이(AGV_FOTA_GATEWAY)로 구현 (7절)

호스트 시험: `tests/host/run.sh`(부트로더·앱 지원 코드·패커), `tests/dsp_ota_host/run.sh`(브리지 `dsp_ota.c` 흐름 — 가짜 UART·HTTP·파티션 + 실제 `bootproto.c`), `make -C tests/bridge_util`(URL 검사·명령 처리). CI `host-test` 가 모두 통과해야 빌드한다.
